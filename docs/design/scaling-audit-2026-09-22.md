# Overcode scaling cliffs: systematic audit of the monitor TUI and daemon

*Working tree of 2026-09-22 (0.5.4 plus uncommitted). Readable edition: the HTML artifact of the same name. Raw record: `scaling-audit-2026-09-22-sites.json` beside this file.*

## Summary

The "110 % CPU for 15 hours" report has a specific, reproducible mechanism. The status bar's burn-rate figure re-parses every live agent's Claude transcript from byte zero once a second with no cache (R1). The worker has no in-progress guard and Textual's exclusive flag does not stop a running thread, so once a pass takes longer than a second the passes overlap and the process pins a core for the rest of its life (R2). On the audit machine, with four agents and 47 MB of reachable transcripts, that path costs 14 % of a core continuously and accounts for 59 % of the TUI's CPU samples; the TUI averaged 24.6 % of a core over 19 hours. Two agents with 200 MB transcripts cross into permanent overlap. The feature is on by default (`TUIPreferences.baseline_minutes` defaults to 60).

Almost every other confirmed site is one of five shapes: whole-file re-parse per tick (sessions.json and daemon state about six times a second; transcripts, history.jsonl and the presence CSV whenever they change); per-agent read-modify-write of one shared file (the daemon rewrites all of sessions.json twice per agent per 2 s loop with fsync); a fresh object that defeats its own cache (`RealTmux()`, `HistoryFile()` constructed per call); unconditional sampling (a history row and a 550-line capture per agent per 2 s regardless of change; every visible row re-rendered at 4 Hz); and two amplifiers (unguarded workers stack threads; a daemon tick over 5 s flips the TUI into capturing every agent at 4 Hz).

No recommendation below is "poll less often". Each site states the freshness its output needs and a fix that keeps it.

## Root causes

Site ids (L2-01, H-19, G1-06 …) refer to the raw record. Critical locations get the verifier's full measurements; the rest of each group is a table.

### R1. Burn-rate window re-parses every live transcript from byte 0, once a second

The status bar's burn figure and the per-row burn column come from `compute_window_burn`. Every second, for every non-asleep agent, it opens every owned transcript and every `subagents/agent-*.jsonl` file and `json.loads` every line from byte zero. There is no cache, no byte offset, no mtime gate. The only gate is `baseline_minutes > 0`, and the dataclass default is 60, so a fresh install has it on.

Measured on this machine with four agents: 47 MB of reachable transcript bytes, 135 to 151 ms per pass, once a second. That is 14 % of a core continuously, and 59 % of all CPU samples taken from the running TUI land in this parse. Real transcripts parse at roughly 250 to 350 MB/s on Apple silicon, so a single 200 MB transcript costs 0.6 to 2.5 s per pass. Past one second per pass the worker overlaps with itself (R2) and the process pins a core for as long as it lives. This is the mechanism behind the 110 % for 15 hours report.

The output is a window average over at least 15 minutes, so a 5 to 30 s lag is invisible. The fix is not a slower timer. It is an incremental per-file reader keyed by (path, mtime, size) holding a byte offset and per-minute token buckets, so each tick parses only appended bytes, plus a stat-only skip of any file whose mtime is older than the window start. That alone removes every historical `/clear` id and every terminated session from the scan without opening them.

Also add an in-progress guard to _fetch_daemon_status_async (as fast/slow paths have) so a slow tick can never stack threads, and move the status-history read to the same incremental pattern.
- **Method:** benchmark — scratchpad/bench_real.py timed read_window_token_usage/_parse_session_lines on the three largest real ~/.claude/projects JSONLs (read-only); synthetic string-heavy lines were 3x faster and discarded. Throughput is json.loads-bound.

### R2. Thread workers have no in-progress guard, so a slow tick stacks threads

Textual's `exclusive=True` cancels only the awaiting asyncio task. A thread worker keeps running to completion. Only the 5 s stats sweep holds an in-progress flag; the 1 s daemon-status worker, the 10 s session refresh, the 30 s timeline, the sister polls and the summarizer do not check `is_cancelled` and have no guard. So the moment any of them takes longer than its period, a second copy starts, then a third. The default executor here has 20 threads, all GIL-bound, and the queue behind them grows for the life of the process.

This is the amplifier that turns every slow site in this report into a permanently pinned core. Fixing it costs nothing in freshness: skip a tick when the previous one is still running, and check the worker's cancel flag between agents.

### R5. Daemon read-modify-writes sessions.json per agent per 2 s loop (agents × file size)

For every agent, every 2 s loop, the daemon loads all of `sessions.json` four to thirteen times and rewrites it twice with `indent=2` plus fsync under an exclusive lock: `update_stats(current_task=…)` is unconditional even when the text has not changed, the time accumulators write every loop, and the parent, children and depth lookups each reload the file. Cost is agents times file size. Measured 13.6 ms per agent at a 50-entry file, so 0.68 s per loop for 50 agents (34 % of a core, 100 fsyncs, 25 MB written); 134 ms per agent at 500 entries, so 6.7 s per loop, at which point the tick exceeds its interval and R6 engages. Issue #292 declined this as won't-fix in March 2026; the 10 s to 2 s loop change in #291 then multiplied it five times.

Nothing here needs sub-tick fidelity: the daemon publishes status from memory each tick already. Build a by-id dict and a children index once per tick from the list it already holds, accumulate mutations in memory, and commit them in one read-modify-write per tick, writing only if something changed. Same 2 s freshness, writes drop from 2N to at most one.

### R6. Stale-daemon fallback: a slow daemon tick makes the TUI capture every agent at 4 Hz

The TUI treats daemon state as stale when it is older than the interval plus 5 s. The same path engages permanently when the daemon is not running. Measured tmux server cost is about 3.7 ms per capture, so this alone saturates the single-threaded server past roughly 38 agents and adds typing lag to every pane on the machine.

R5 pushes a daemon tick past 5 s at about 25 agents with 2,000 sessions; R7 does it at about 120 agents regardless. So the cascade is: file grows, daemon slows, TUI compensates by hammering tmux. The fix is to stop compensating: rotate non-focused captures regardless of daemon freshness (adaptive period so per-tick captures cap near 12), have the daemon publish its tick duration so slow-but-alive is not stale, and show a staleness banner. Focused-pane latency stays 250 ms.

### R10. Status-history CSV: one row per agent per 2 s regardless of change

`log_agent_status` writes one CSV row per agent every 2 s whether or not anything changed: 25 rows a second at 50 agents, about 170 MB a day raw. Everything downstream scales with agents times hours. The TUI keeps every row in the window in memory (270,000 tuples, 80 to 100 MB, at 50 agents over the default 3 h; a 24 h timeline reaches gigabytes). The 1 Hz mean-spin pass does a list membership test per row. Hourly rotation rewrites a file over 50 MB synchronously inside the daemon loop from about 8 agents upward. Timeline bucketing runs on the main thread and crosses 100 ms per keypress at about 50 agent-hours.

Timeline slots are 30 s and the spin mean is a 15-minute-plus average, so none of this needs a sample every 2 s. Log on status change plus a periodic keepalive row (10 to 50 times fewer rows, identical output), then trim the cached window with a deque, keep per-agent run-length segments, and bucket in the worker.

### R17. In-memory growth over uptime

`_mark_event` appends to an in-memory list about 11 times a second, and the flush timer that drains it only exists when event-loop timing is enabled; with it disabled the list is never emptied and passes 100 MB after about 15 hours and 1 GB after a week. The per-session dicts in the TUI, the detectors and RealTmux are never pruned, though each entry is tiny.

Return early when the probe is disabled, cap the buffer, and prune the preference sets to live sessions.

## Cross-cutting findings

**Nothing is gated on anyone watching.** Every TUI timer runs at full rate for the life of the process: when no tmux client is attached, when the window is inactive, when the screen is locked. Only the summarizer pauses on idle. The stall bell is the only output that matters while unattended and can be derived from daemon-published status at 2 s without a pane capture. A low-power mode when no client is attached is the largest single saving available and costs zero visible freshness.

**The 5 s timers are phase-aligned.** The 5, 10, 15 and 30 s timers fire in the same instant, so every fifth second starts an 8-thread executor, git subprocesses, a tmux list-windows and several main-thread apply callbacks together; the TUI's own event-loop probe shows main-thread stalls over 150 ms are seven times more frequent inside that window. Offsetting the timers spreads the burst without changing any cadence.

**One tmux server, one thread, everybody's commands.** Every overcode TUI, daemon, web server, hook handler and follower on the host talks to the same tmux server at 2.5-3.7 ms per command. At reference (50 agents, hooks mode, healthy daemon): TUI fast path ~54 captures/s, daemon ~25 captures + 20 pid lookups/s, web tier 250 commands per status request. Typing latency in every pane degrades from roughly 120 ms of server time per second. Command count, not capture depth, is what to budget.

**Mac numbers, Linux fleets.** Benchmarks ran on a 16-core Apple-silicon Mac with APFS. JSON parse throughput on Linux is typically 2-3x lower and ext4 fsync an order of magnitude slower, so the transcript sites (R1, R3) and the fsync-per-agent site (R5) are worse on the colleague's machine.

## Fix programme (keeps every number as fresh as today)

1. **One incremental transcript reader, shared.** Per-file (path, mtime, size, byte offset) state with additive totals and per-minute usage buckets, used by both the burn window (R1) and the stats sweep (R3), plus a stat-only skip of files older than the window. Guard: a synthetic 1 GB transcript must cost under 5 ms per tick once warm.
2. **Guard every thread worker.** Skip a tick if the previous one is still running; check the cancel flag between agents (R2). Publish the daemon's tick duration and use it in the staleness test; rotate non-focused captures regardless of daemon freshness (R6).
3. **mtime-gated parse caches on the shared files.** `SessionManager._load_state` and `MonitorDaemonState.load` return the previous object when (mtime_ns, size) is unchanged (R4).
4. **One read, one write per daemon tick.** Build by-id and children indexes from the list the tick already holds, accumulate stat mutations in memory, commit once, write only on change; compare-before-write in every setter (R5). Archive terminated sessions out of the live file.
5. **Count tmux commands, then cut them at source.** Persistent RealTmux in the daemon and web tier; one `list-panes -F` for pids and pane activity per sync; capture only panes whose activity changed, 40 lines for enrichment (R7, R9, R11).
6. **Log status changes, not samples.** A history row on change plus a periodic keepalive, byte-based hook-log rotation with truncated inputs, presence tail-reads (R10, R12, R13).

## Side findings (not performance)

- `_count_untracked_windows` calls `tmux.session_exists(...)`, but `RealTmux` only defines `has_session`; the untracked-window count every 120 s is effectively dead or raising.
- Auto-archive never archives: `_auto_archive_done_agents` kills the window and sets status `terminated`; nothing moves the entry to `archive.json`, so terminated sessions stay in the live file (and in the burn scan) until manual cleanup.
- `clear_old_history` is dead code (no callers).
- `count_interventions_from_log` in the supervisor is dead code with real cost (reads the whole supervisor log, two timestamp formats per line, on every completion).
- A duplicate agent name forming a parent/child cycle crashes the daemon in `_compute_subtree_costs`.
- The hook-event log rotation trims by line count (200) but triggers by bytes (100 KB); once lines average over 512 bytes the file is rewritten on every event.

## Method and caveats

Sixteen mapping agents each took one subsystem and listed every per-tick calculation with its trigger chain, cadence, axes and bound, citing file and line. Three more mined git history, GitHub issues and PRs, and the repo's own audit documents. A completeness critic walked the tree for anything unclaimed and spawned three more mappers (the tmux command budget, visibility gating, timer phase alignment). Every resulting site went to an independent verifier that first tried to refute it by finding an existing gate, then costed the survivors at reference scale, running a micro-benchmark on synthetic data where cheap. Sixty-nine agents in total; nothing under `~/.overcode` or `~/.claude` was written to.

Caveats: benchmarks are single-machine (Apple silicon, APFS) and synthetic where noted; verifiers flagged where synthetic lines overstate real parse speed by 3-5x and real-transcript figures were preferred. Line numbers are as of the working tree on 2026-09-22 including uncommitted edits to `hook_status_detector.py`. Severity is a judgment from cost, not a measurement of the reporting colleague's machine.
